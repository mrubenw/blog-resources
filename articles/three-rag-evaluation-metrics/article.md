# Three RAG Evaluation Metrics

In a previous article, we built a multimodal RAG pipeline end to end: we’re starting from embedding images and text into a shared space with CLIP, storing them in a vector database, retrieving the most relevant images for a query, and letting a Vision-Language Model generate an answer grounded in them. By the end it produced genuinely useful answers, and it would have been easy to call the job done right there.

But there's a problem we quietly stepped over: we don't actually know how good that system is. A RAG pipeline can hand us a confident, fluent, well-structured answer that happens to be completely wrong, and reading one or two examples by hand won't tell us whether that's a fluke or the norm. The only way to know for sure is to measure it and in this article, we’re going to talk about three metrics that, taken together, tell us not just *whether* our RAG system works, but *which part* of it works and which part doesn't.

When we read that answer, it *looks* great. But "looks great when I read one example" is not a quality metric, it's a vibe. In production, our system answers thousands of queries we'll never read by hand, and any of them could go wrong in ways that aren't visible from the answer text alone. Consider what could be silently broken:

- The retriever could pull back **irrelevant images**, and the VLM could still produce a plausible answer from its own pre-trained knowledge. Therefore, the answer would look fine, but the retrieval is useless.
- The VLM could **ignore the retrieved images entirely** and hallucinate, and we'd never know unless we checked the answer against the actual context.
- The answer could be perfectly grounded in the images but **not actually address the question**.

The point is that "is this a good RAG response?" isn't one question, it's *three*, and they fail independently. We need metrics that pull these apart, so that when something goes wrong we know not just *that* it's broken but *which part* is broken. That's exactly what these three RAG metrics give us.

## The three metrics

Each metric isolates a different stage of the pipeline:

- **Answer Relevance:** How well does the generated answer address the original query? This checks the *generation* step's output against the user's intent. An answer can be fluent and factual but still fail here if it doesn't actually answer what was asked.
- **Context Relevance:** How relevant is the retrieved context (in our case, the images) to the query? This checks the *retrieval* step. If this is low, our retriever is handing the generator the wrong material to begin with.
- **Faithfulness:** How accurately does the answer reflect the retrieved context? This checks whether the generator actually *used* the retrieved images, rather than making things up. A faithful answer is grounded in the context; an unfaithful one drifts away from it.

The beautiful thing about having three separate metrics is that, between them, they triangulate the failure. Retrieval problems show up in context relevance, grounding problems show up in faithfulness, and generation problems show up in answer relevance. We'll see exactly how once we've computed them.

## Measuring the metrics with an LLM-as-a-Judge

How do we actually *compute* these metrics? 

We can't write a simple formula for "how relevant is this image to this question" since it requires judgment. Humans are inherently biased and flawed when judging the quality of answer generated by LLMs, therefore what we can do instead is that we use the **LLM-as-a-Judge** approach: we hand the query, the answer, and the retrieved images to a powerful, separate model and ask *it* to score each metric from 0.0 to 1.0. Since our context is images, the judge has to be multimodal too. In this article, we’re going to use Claude Sonnet.

Each metric is really just a carefully worded prompt. You’re free to word the prompt according to your taste, but let's look at the example of all three.

### Faithfulness

For faithfulness, we give the judge the query, the answer, and the retrieved images, and ask whether the answer is actually supported by what's visible:

```python
prompt = f"""
Evaluate the faithfulness of the generated answer based on the provided images.

Query: {example.query}
Generated Answer: {example.generated_answer}

Look at the provided images and determine:
1. Does the generated answer accurately describe what's shown in the images?
2. Is the answer consistent with the visual content?
3. Does the answer contain any information that contradicts what's visible?

Rate faithfulness on a scale of 0.0 to 1.0 where:
- 1.0: Answer is completely faithful to the visual evidence
- 0.5: Answer is partially faithful with some unsupported claims
- 0.0: Answer contradicts or is not supported by the evidence

Respond with only the numerical score (e.g., 0.8).
"""
```

The retrieved images are attached to the message alongside this prompt, so the judge can literally look at them while it scores.

### Context relevance

Context relevance doesn't need the answer at all: it only asks whether the *retrieved images* are useful for the query. So we pass the query and the images, and leave the answer out:

```python
prompt = f"""
Evaluate how relevant these images are for answering the following query:

Query: {example.query}

Look at the provided images and rate their relevance on a scale of 0.0 to 1.0:
- 1.0: Images are highly relevant and contain information needed to answer the query
- 0.5: Images are somewhat relevant but may be missing key information
- 0.0: Images are not relevant to the query

Respond with only the numerical score (e.g., 0.7).
"""
```

This is the one metric that judges the retriever in isolation, which is what makes it so useful for localizing a retrieval problem later.

### Answer relevance

Answer relevance is the opposite: it doesn't need the images, only the query and the answer. It's a pure text judgment of whether the answer addresses what was asked:

```python
prompt = f"""
Evaluate how well the given answer addresses the original query.

Original Query: {query}
Generated Answer: {answer}

Evaluate the answer based on:
1. Direct Relevance: Does the answer directly address what was asked?
2. Completeness: Does it provide sufficient information to satisfy the query?
3. Focus: Is it focused on the query without unnecessary tangents?
4. Appropriateness: Is it appropriate for the type of question asked?

Rate answer relevance on a scale of 0.0 to 1.0 where:
- 1.0: Perfectly addresses the query with complete, focused information
- 0.6: Partially addresses the query but misses some key aspects
- 0.2: Barely relates to the query
- 0.0: Completely irrelevant to the query

Respond with only the numerical score (e.g., 0.85).
"""
```

### Running the judge

All three prompts share the same machinery. We send the prompt (plus images, where relevant) to the model, set `temperature=0` so the scoring is as deterministic as possible, parse the single number out of the response, and clamp it to `[0.0, 1.0]` to be safe against the occasional stray output:

```python
response = self.openai_client.chat.completions.create(
    model=self.openai_model,       # chatgpt-4o-latest
    messages=messages,
    max_tokens=10,
    temperature=0,
)
score = float(response.choices[0].message.content.strip())
return max(0.0, min(1.0, score))
```

## Putting the metrics to the test

Three numbers are only useful if we trust that they actually measure what they claim to. The best way to build that trust and the intuition that goes with it, based on my experience, is to deliberately break things and watch the scores react.

Rather than typing in a fake answer or picking an unrelated image by hand, we get every (answer, context) pair from the *real* pipeline built in the previous article, run twice with two genuinely different queries:

- **Query A**, the on-topic steak question, run through the full pipeline (CLIP retrieval + Claude generation) gives us a real `(answer_a, context_a)` pair — our good baseline.
- **Query B**, an unrelated question about a bowl of ice cream, run through the same pipeline gives us a real `(answer_b, context_b)` pair — a genuinely bad answer and genuinely irrelevant context, with zero manual editing.
- One more real generation call — Query B's text, but handing the model `context_a` (the steak images) instead of its own retrieved images — gives us `answer_offtopic`: a real, off-topic answer that's still grounded in *something*, just the wrong thing.

Four test scenarios then fall out of just recombining these three real artifacts, always judged against Query A:

| Scenario | Answer | Retrieved context |
| --- | --- | --- |
| 1. Everything correct | `answer_a` | `context_a` (4 relevant steak images) |
| 2. Off-topic answer | `answer_offtopic` | `context_a` (4 relevant steak images) |
| 3. Wrong context | `answer_a` | `context_b` (ice cream images) |
| 4. Both degraded | `answer_b` | `context_b` (ice cream images) |

Nothing here is hand-picked or hand-written — every answer and every image is something the real pipeline actually produced. All we control is which real output we pair with which.

Running `notebooks/rag_evaluation.ipynb` end to end (after building the index in the previous article's notebook) prints exactly this table, filled in with real scores from that run:

| Scenario | Answer | Retrieved context | Faithfulness | Context Rel. | Answer Rel. |
| --- | --- | --- | --- | --- | --- |
| 1. Everything correct | `answer_a` | `context_a` (steak images) | | | |
| 2. Off-topic answer | `answer_offtopic` | `context_a` (steak images) | | | |
| 3. Wrong context | `answer_a` | `context_b` (ice cream images) | | | |
| 4. Both degraded | `answer_b` | `context_b` (ice cream images) | | | |

Let's walk through what each scenario should show, and why.

**Scenario 1: everything works.** All three metrics should land near 1.0. The retrieved images are relevant to the steak query (context relevance), the answer was actually generated from them (faithfulness), and it addresses what was asked (answer relevance). This is the baseline.

**Scenario 2: the answer comes from an unrelated question, but the context stays the on-topic steak images.** Context relevance is judged against the steak query and the steak images are untouched, so it should **stay high** — the retriever did nothing wrong here. But the answer is about ice cream, grounded in nothing the steak images show and not addressing the steak question at all, so **faithfulness and answer relevance should both collapse**. The metrics localize the failure cleanly: they point at generation and leave retrieval blameless.

**Scenario 3: the answer stays the real, on-topic steak answer, but the context becomes the ice-cream images.** Now the divergence gets interesting.

- **Answer relevance should stay high**, since the answer itself still addresses the steak question perfectly — nothing about the *answer* changed.
- **Context relevance should collapse**, because ice cream images tell you nothing about side dishes for steak.
- **Faithfulness should collapse too**: the answer talks about things like potatoes, vegetables, or sauces that don't appear anywhere in a bowl of ice cream.

This is the most instructive case: it shows that a *good answer* can still be *unfaithful*, because faithfulness is about the relationship between the answer and the context, not the answer's quality in isolation.

**Scenario 4: both the answer and the context come from the same unrelated ice-cream run.** Judged against the steak query, all three metrics should be low — the context isn't relevant, the answer doesn't address the steak question, and (since the ice-cream answer is presumably grounded in the ice-cream images) faithfulness *to the ice-cream context* may be reasonably high even though it's irrelevant here. Faithfulness measures groundedness, not relevance — a fully faithful answer to the wrong context is still a bad response to the query it's being judged against.

Because the judge returns a continuous score rather than a binary pass/fail, expect some of these to land at partial values rather than exactly 0.0 or 1.0 — that's the LLM-as-a-judge hedging on genuinely ambiguous cases, not noise to be ignored.

## Turning scores into fixes

The reason we bother splitting quality into three numbers is that each one points to a different resolution. Once we know *which* metric is low, we know *what* to go fix:

- **Low context relevance** → the problem is **retrieval**. Improve your embeddings, your chunking, or your retriever configuration (try a different similarity metric, retrieve more candidates, add a reranking stage).
- **Low faithfulness** → the problem is **grounding**. Tighten the prompt so the model is instructed to rely on the context, or add a context-filtering step so only genuinely relevant material reaches the generator.
- **Low answer relevance** → the problem is **generation**. Tune the generation settings (temperature, prompt format), or try a different LLM/VLM.

## Conclusion

In this article, we turned a vague sense that our RAG system "seems to work" into three concrete numbers. Using LLM-as-a-judge approach, we measured faithfulness, context relevance, and answer relevance, and by deliberately breaking each part of the pipeline we saw how those numbers localize exactly where a RAG system goes wrong: retrieval, grounding, or generation.
